## 1. Final group sizing state can arrive after strategies cache it for the following day

**Claim / position:** The new automatic group finish/cushion state does not reliably apply the completed closing state to the next trading day. In active ONB, `apex_strategies/NQ_Overnight_Bias_ADX30.txt:208–215` changes the key at 16:00, reads the group flag, and caches it for that key. A cached `EVAL_FULL` then overrides even fresh own-account equity at or above $156,000 (lines 221–223); entry sizing uses the result at line 231.

**Evidence:** The regular intraday writer ends at 15:15 (`live/vps/push_trade_logs.ps1:20–24`). The closing push runs at 16:10 (lines 1–4), invoking `cushion_peak.ps1` at line 43. `apex_strategies/Apex_Chart_Guard.txt:155–173` supplies account scans at 15:55–16:00; `live/vps/cushion_peak.ps1:67–76` writes the resulting group flags. Thus a 16:00 strategy calculation can cache the provisional group state before the final writer. On consecutive weekdays, `Date+1` before midnight and `Date` afterward are the same key, so the 16:10 update is not read before the next day's entries. The same finish-cache pattern appears in Twin and Dual Thrust; funded group cushion readers have the same timing, e.g. `Twin_Continuation_150K.txt:513–526`.

**Reproduction / consequence:** Toy Wednesday 16:00 caches `EVAL_FULL`, final 16:10 writer changes to `EVAL_FINISH`, and Thursday 09:00 retains full 10 contracts instead of intended 5 despite equity $156,100. The reverse change can retain half size when full size is intended. A funded follower's smaller updated cushion can likewise remain stale. ONB is reachable as `ONB150-5` in `live/expected_setup.json`; this is not confined to retired VB. Current #5 was below the finish threshold this week, and the committed group log reports zero funded accounts; no actual wrongly sized trade is claimed.

**Counterevidence:** Fresh leader equity and the local funded peak tracker preserve parts of the leader's own state. They do not refresh the group override. Restarting after 16:10, no relevant closing change after 15:15, or a chart that first calculates after the final write avoids this case.

**Smallest settling check:** Use synthetic flag files and the existing cache equations: read provisional FULL at 16:00, replace it with final FINISH at 16:10, then size a next-day entry. Require 5, not 10. A fix should identify the completed state date or refresh after the final writer rather than latch an undated flag for the whole next day. No strategy backtest is needed to settle this state-transition defect.

## 2. Failed rejection notifications are consumed before delivery, so the new retry handling loses them

**Claim / position:** The November 10 alert retry patch preserves delivery timestamps on failure, but its rejection alert path still advances the detection cursor before a notification succeeds. `live/vps/watchdog.ps1:159–164` generates a problem only when `$rej > $prev`; line 165 then stores the new `rej_count` unconditionally. The catch at lines 188–190 records `SEND_FAILED`; line 194 persists that already advanced count.

**Evidence / consequence:** Actual extracted detection and delivery blocks were run twice with one synthetic rejection. Run one generated one problem, attempted delivery once, received the stubbed failure, and persisted `rej_count=1` with no `sent_REJECT` timestamp. Run two recovered network delivery but had the unchanged rejection count: zero generated problems and still only one lifetime delivery attempt. Therefore a transient ntfy failure permanently loses that rejection alert unless another rejection later increases the count. This can hide the first order rejection that needs intervention, including the lead-up to MultiCharts disabling auto-trading after repeated rejects. No real notification was sent during the check.

**Counterevidence:** Ordinary standing conditions are generated again and retry after a failed send; successful rejection sends work. The new catch reports failure in the local log and exits 1. Those properties do not re-create the consumed rejection event. I found no committed evidence proving a real failed rejection delivery this week, so this is a confirmed fault-path defect, not a claim that the November 13 alert was lost.

**Smallest settling check:** Repeat the two-run stubbed-send check with no new rejection on run two; require two delivery attempts and retention until acknowledgement. Move rejection acknowledgement to successful delivery or persist a pending rejection event separately from the scan count. Also retain the existing mute policy explicitly when deciding when to acknowledge.
